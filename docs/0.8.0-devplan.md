## Version Objective

v0.8.0 is a **configuration-UI feature** release. It adds, inside the existing
web configuration interface (`/config`), two capabilities centred on the local
`pictures/` artwork folder and the public-endpoint artwork query:

1. **Picture library management** — directly from `/config` the user can:
   - see the **list of image files** currently in `pictures/` (the folder used by
     artwork *folder* mode), each row with a **delete** icon and a **rename**
     icon;
   - **upload** a new image via a button (multipart upload);
   - **rename** a file inline: pressing the rename icon turns the file name into a
     text input (pre-filled with the current name) flanked by **Salva** and
     **Annulla** icons that apply or cancel the rename.

2. **Artwork query test/preview** — in the artwork section (the ARTIC public
   endpoint query) a **Test** button performs a *dry-run*: it fetches one image
   matching the current query and shows an inline preview + caption, without
   changing any state.

These are additive UI/server features. The rendering pipeline, the e-ink loop,
artwork *folder* / *endpoint* behaviour, and the config schema are unchanged
(no new config fields). The pictures folder is mutated on disk directly; because
the renderer rescans the folder on every render (`list_folder_images` is called
inside `load_folder_artwork`), picture changes take effect on the next artwork
frame **without** a config reload / SIGHUP.

**Release closure criterion:** from `/config` a user can list, upload, rename,
and delete files in `pictures/`, and can preview an endpoint-query result; all
new endpoints are auth-protected, reject path traversal and non-image content,
and the full test suite is green.

## Invariant Constraints

Constraints from previous versions remain valid. In particular for v0.8.0:

- **Auth on every mutating/reading endpoint**: all new routes carry
  `dependencies=[Depends(require_config_auth)]`, exactly like the existing
  `/config`, `/api/test-*`, `/api/config/*` routes.
- **No path traversal, no arbitrary write/delete**: every operation that names a
  file resolves to a path **inside** the configured artwork folder and rejects
  anything else (`..`, absolute paths, separators, symlink escape). This is the
  central security requirement of the release.
- **Image-only**: uploads are validated as real images (extension in
  `_FOLDER_IMAGE_EXTS` **and** openable by Pillow); non-images are rejected.
- **No raw large-file serving**: list rows and previews use PIL-downscaled
  thumbnails — the folder holds multi-megabyte JPEGs and must never be streamed
  verbatim into the browser.
- **Single rendering source unchanged**: `PillowEinkRenderer.render()` remains
  the only image producer; this release does not touch the renderer's output.
- **Folder changes need no reload**: mutating `pictures/` must not require a
  SIGHUP; the renderer already rescans the folder per render. The config YAML is
  not rewritten by any picture operation.

## Phase 1 — Folder-Path Helper (single source of truth)

**Goal:** one function resolves `config.artwork.folder` to an absolute path so
the renderer and the new routes agree on which directory is "the pictures
folder". Today the resolution logic lives inline in
[pillow_eink_renderer.py:98-104](../app/renderer/pillow_eink_renderer.py#L98).

### 1.1 — Add `resolve_artwork_folder`

In [app/renderer/components/artwork.py](../app/renderer/components/artwork.py)
add:

```python
# Project root = three levels above this file: app/renderer/components/ -> project/
_PROJECT_ROOT = Path(__file__).resolve().parents[3]


def resolve_artwork_folder(folder: "str | Path") -> Path:
    """Resolve a configured artwork folder to an absolute path.

    Relative paths resolve against the project root (matching the renderer's
    historical behaviour). The path is returned resolved (symlinks collapsed) so
    callers can safely use it as a containment boundary.
    """
    p = Path(folder)
    if not p.is_absolute():
        p = _PROJECT_ROOT / p
    return p.resolve()
```

> Verify `parents[3]` lands on the project root from `components/`. The renderer
> uses `parents[2]` from `app/renderer/`; from `app/renderer/components/` the
> root is one level deeper. Add a unit assertion in Phase 6 rather than trusting
> the index.

### 1.2 — Refactor the renderer to use it

In [pillow_eink_renderer.py:101-104](../app/renderer/pillow_eink_renderer.py#L101)
replace the inline `Path(_folder) … parents[2]` block with
`resolve_artwork_folder(_folder)`. Behaviour is identical; this removes the
duplicate path math.

## Phase 2 — Picture Service Layer

**Goal:** pure, testable functions for the four operations + thumbnailing, with
**path-containment** as a hard guarantee. No FastAPI here — these are called by
Phase 3 and unit-tested directly.

Create [app/server/pictures.py](../app/server/pictures.py):

### 2.1 — Safe name resolution (the security core)

```python
class PictureError(ValueError):
    """Raised for invalid picture names / unsupported content."""


def safe_picture_path(folder: Path, name: str) -> Path:
    """Resolve *name* to a path guaranteed to sit directly inside *folder*.

    Rejects: empty names, names containing path separators or '..', absolute
    paths, dotfiles, and any resolved path that escapes *folder* (symlink or
    otherwise). Raises PictureError on any violation.
    """
    raw = (name or "").strip()
    if not raw or raw.startswith(".") or "/" in raw or "\\" in raw or raw in ("..", "."):
        raise PictureError(f"Nome file non valido: {name!r}")
    candidate = (folder / raw).resolve()
    if candidate.parent != folder.resolve():
        raise PictureError("Percorso fuori dalla cartella consentita.")
    return candidate
```

> Containment is checked with `candidate.parent != folder.resolve()` rather than
> a `str.startswith` prefix test (which is fooled by sibling dirs like
> `pictures-evil`). The extension whitelist is enforced separately (2.3/2.4).

### 2.3 — Saving an upload

```python
def save_upload(folder: Path, filename: str, data: bytes,
                *, max_bytes: int = 25 * 1024 * 1024) -> str:
    """Validate and write an uploaded image; return the stored file name.

    - sanitise the client filename through safe_picture_path;
    - reject extensions not in _FOLDER_IMAGE_EXTS;
    - reject data larger than max_bytes;
    - verify the bytes are a real image (Image.open(BytesIO(data)).verify());
    - on name collision, suffix '-1', '-2', … rather than overwriting.
    """
```

> `Image.verify()` invalidates the object, so re-open if you also need to read
> it; here verification alone is enough. Write atomically (temp file in the same
> dir + `os.replace`) so a crash mid-write can't leave a truncated image that the
> renderer would later fail to open.

## Phase 3 — Picture REST Endpoints

**Goal:** thin FastAPI handlers over Phase 2, all auth-protected, added to the
existing router in [app/server/routes/config.py](../app/server/routes/config.py).
Each handler resolves the folder once via
`resolve_artwork_folder(request.app.state.config.artwork.folder)`.

| Method & path | Purpose | Body / params | Response |
|---|---|---|---|
| `GET /api/pictures` | list files | — | JSON `{ok, folder, pictures:[{name,size_bytes,modified_iso}]}` |
| `GET /api/pictures/thumbnail` | row thumbnail | `?name=` | `image/jpeg` (PIL-resized) |
| `POST /api/pictures/upload` | upload one image | multipart `file` | JSON `{ok, name}` or `{ok:false, message}` |
| `POST /api/pictures/rename` | rename | form `old`, `new` | JSON `{ok, name}` or `{ok:false, message}` |
| `POST /api/pictures/delete` | delete | form `name` | JSON `{ok}` or `{ok:false, message}` |

Implementation notes:

- All five carry `dependencies=[Depends(require_config_auth)]`.
- Catch `PictureError` and return `JSONResponse({"ok": False, "message": str(exc)})`
  with `status_code=400`; never leak a stack trace or absolute path to the
  client (log full detail server-side, return a short Italian message — matching
  the existing `_str` message style).
- `upload` reads `await file.read()` and forwards to `save_upload`; enforce the
  size cap there (don't trust `Content-Length`).
- `thumbnail` sets `Cache-Control: no-store` (names are reused after rename, so a
  cached thumbnail could go stale) and returns 404 → `{ok:false}` for missing
  files.
- **No SIGHUP / no config write** in any of these — picture changes are picked up
  by the renderer's per-render folder scan. (Document this explicitly in the
  handler docstrings so a future maintainer doesn't "helpfully" add a reload.)

**Acceptance — Phase 3:**

```bash
# with the dev server running and auth configured:
curl -s -u user:pass http://localhost:8080/api/pictures | jq '.ok, (.pictures|length)'
curl -s -u user:pass -F file=@sample.jpg http://localhost:8080/api/pictures/upload | jq .ok   # true
curl -s -u user:pass --data 'name=../config/default.yaml' \
     http://localhost:8080/api/pictures/delete | jq .ok                                        # false (blocked)
```

## Phase 4 — Artwork Query Preview (dry-run)

**Goal:** a Test button in the artwork section fetches one image for the current
query and returns a preview + caption, changing nothing.

Add to [routes/config.py](../app/server/routes/config.py), mirroring
`/api/test-weather`:

```python
@router.post("/api/test-artwork", dependencies=[Depends(require_config_auth)])
async def test_artwork(request: Request) -> JSONResponse:
    """Dry-run: fetch one artwork for the submitted query and return a preview.

    Does not touch config or the display. Returns the caption and a small
    base64 PNG data URI so the UI can show it inline.
    """
```

- Read `query` from the form, falling back to `ARTWORK_QUERY_DEFAULT`.
- Call `fetch_artwork(width, height, query, eink_enhance=False)` at a **preview
  size** (e.g. fit into the display resolution capped at ~640 px wide — a true
  full-panel fetch is unnecessary for a thumbnail and slower). Reuse
  `config.display.resolution` for aspect ratio.
- `fetch_artwork` already performs the network call with retries and returns
  `(image, caption)` or `None`. On `None`, return
  `{"ok": False, "message": "Nessun artwork trovato per questa query."}`.
- On success, encode the image to PNG → base64 → `data:image/png;base64,…` and
  return `{"ok": True, "caption": caption, "image": data_uri}`.

> Run the blocking `fetch_artwork` in a thread (`await
> anyio.to_thread.run_sync(...)` or `run_in_executor`) so the network fetch does
> not block the event loop — `test-weather` calls `_fetch()` synchronously today,
> but artwork fetches images (slower, up to 5 attempts × 15 s). Keep a tight
> overall timeout so the button can't hang the UI.

**Acceptance — Phase 4:**

```bash
curl -s -u user:pass --data 'query=mountain landscape' \
     http://localhost:8080/api/test-artwork | jq '.ok, (.image|startswith("data:image/png;base64,"))'
# -> true, true (when online); ok:false with message when the API is unreachable
```

## Phase 6 — Tests

**Goal:** cover the security-critical service layer and the endpoints.

### 6.1 — `tests/test_pictures_service.py`

- `safe_picture_path`: accepts a plain name; rejects `..`, `../x`, `/abs/path`,

## Out of Scope

- New `ArtworkConfig` fields, multiple folders, or per-image metadata/captions.
- Image editing (crop/rotate/adjust) in the browser — uploads are stored as-is;
  the renderer's existing `ImageOps.fit` + `enhance_for_eink` handle fit/colour.
- Drag-and-drop reordering or manual ordering — folder mode stays alphabetical.
- Bulk operations (multi-select delete, zip upload) — single-file operations only.
- Changing the artwork source/provider, the ARTIC integration, or the e-ink
  enhancement pipeline.
- Persisting previews or caching fetched artworks to disk — the Test button is a
  transient dry-run.
