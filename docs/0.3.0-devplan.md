## Obiettivo della versione

v0.3.0 completa il progetto in due fasi sequenziali:

1. **Completamento v0.2.0** — chiude tutti i file troncati e i route handler mancanti lasciati incompleti al termine di v0.2.0 (template HTML, provider ICS, route config).
2. **Migrazione a PlaywrightRenderer** — sostituisce `ImageRenderer` (Pillow) con `PlaywrightRenderer` (Playwright Chromium headless) come fonte unica di rendering, allineando il codice all'architettura descritta in `docs/architecture.md`. I template HTML Jinja2 diventano la sorgente visuale di riferimento per entrambi i display. `HdmiDisplay` viene refactorizzato da subprocess Chromium a Playwright non-headless. HTMX cablato per la navigazione.

---

## Vincoli invarianti (da rispettare in ogni fase)

- `PlaywrightRenderer` è la fonte unica di rendering — nessuna duplicazione in Pillow per display fisici
- Le librerie Waveshare sono sempre importate dinamicamente, protette da `display.type == "eink"`
- `playwright_executable` configurabile (null = bundle Playwright; `/usr/bin/chromium-browser` su RPi)
- Le credenziali CalDAV/iCal non appaiono mai in log, output API o messaggi di errore
- Tutti i percorsi file usano `pathlib.Path`
- Logging standard (`logging`) — nessun `print` diagnostico
- Type hints obbligatori su tutte le funzioni pubbliche
- Nessun `box-shadow`, `border-radius`, `text-shadow` nei template HTML
- CSS usa esclusivamente `px` — nessun `rem`, `em`, `vw`, `vh`
- HTMX incluso come asset locale in `base.html` — non è un pacchetto pip

## Fase 2 — HTMX: cablaggio navigazione

**Goal:** i pulsanti footer in `base.html` inviano azioni di navigazione al server via HTMX; il DOM si aggiorna senza full-page reload. I pulsanti nascosti con ID specifici sono presenti nel DOM per Playwright `page.click()`.

*Dipende da: Fase 1 (route handler completi).*

### 2.1 — Aggiungere HTMX come asset locale

**File:** `app/assets/htmx.min.js` (scaricare htmx 2.x da https://htmx.org/dist/htmx.min.js)

Registrare la directory `app/assets/` come `StaticFiles` in `app/server/app.py`:
```python
from fastapi.staticfiles import StaticFiles
app.mount("/assets", StaticFiles(directory=str(Path(__file__).parent.parent / "assets")), name="assets")
```

**Criteri di accettazione:** `GET /assets/htmx.min.js` restituisce 200.

### 2.2 — Caricare HTMX e aggiungere pulsanti navigazione in `base.html`

**File:** `app/server/templates/base.html`

1. Aggiungere nel `<head>`:
   ```html
   <script src="/assets/htmx.min.js" defer></script>
   ```

2. Aggiungere nella sezione `<body>`, prima del tag `</body>`, un overlay di navigazione visibile solo se `show_buttons` è true:
   ```html
   <div class="nav-overlay {{ '' if show_buttons else 'nav-overlay--hidden' }}">
     <button id="btn-nav-out"   hx-post="/state" hx-vals='{"action":"out"}'   hx-target="body" hx-swap="outerHTML" type="button">↑</button>
     <button id="btn-nav-prev"  hx-post="/state" hx-vals='{"action":"prev"}'  hx-target="body" hx-swap="outerHTML" type="button">←</button>
     <button id="btn-nav-next"  hx-post="/state" hx-vals='{"action":"next"}'  hx-target="body" hx-swap="outerHTML" type="button">→</button>
     <button id="btn-nav-in"    hx-post="/state" hx-vals='{"action":"in"}'    hx-target="body" hx-swap="outerHTML" type="button">↓</button>
     <button id="btn-nav-night" hx-post="/state" hx-vals='{"action":"night"}' hx-target="body" hx-swap="outerHTML" type="button">☾</button>
   </div>
   ```
   `.nav-overlay--hidden` applica `visibility: hidden; pointer-events: none` — i pulsanti rimangono nel DOM per `page.click()`.

**Criteri di accettazione:** click su un pulsante nel browser aggiorna la vista senza reload completo; `show_buttons: false` nasconde i pulsanti visivamente ma li mantiene nel DOM.

### 2.3 — Aggiornare `POST /state` per restituire HTML

**File:** `app/server/routes/state.py`

Dopo l'aggiornamento dello stato, `POST /state` deve restituire il contenuto HTML della nuova vista (come farebbe `GET /`). Estrarre la logica di rendering da `routes/index.py` in una funzione `_render_view(request) -> TemplateResponse`, condivisa tra `GET /` e `POST /state`.

Il rilevamento della richiesta HTMX avviene tramite header `HX-Request: true`:
```python

    return await _render_view(request)
return JSONResponse(new_state.model_dump())
```

**Criteri di accettazione:** un `POST /state` con `{"action": "next"}` restituisce HTML 200 con il contenuto della nuova vista; HTMX sostituisce il `<body>` correttamente.

## Fase 3 — PlaywrightRenderer

**Goal:** nuovo `app/renderer/playwright_renderer.py` che mantiene l'istanza Chromium headless persistente, gestisce `NavigationState` con thread-safety, e produce `PIL.Image` tramite screenshot.

*Dipende da: Fase 2 (HTMX + route /state aggiornati).*

### 3.1 — Creare `app/renderer/playwright_renderer.py`

**Classe `PlaywrightRenderer`** — implementa l'interfaccia di `app/renderer/base.py`:

```python
class PlaywrightRenderer:
    def __init__(self, config: AppConfig, aggregator: CalendarAggregator) -> None: ...
    def start(self, port: int) -> None: ...         # launch Playwright headless
    def screenshot(self) -> Image.Image: ...         # page.reload() + screenshot → PIL.Image
    def get_state(self) -> NavigationState: ...      # thread-safe read
    def update_state(self, new_state: NavigationState) -> None: ...  # thread-safe write
    def click_nav(self, action: str) -> None: ...    # page.click(f"#btn-nav-{action}")
    def stop(self) -> None: ...                      # browser.close()
```

**Dettagli implementativi:**
- Avvio: `sync_playwright().start()` → `playwright.chromium.launch(headless=True, executable_path=...)` → `browser.new_context(viewport={"width": W, "height": H})` → `page.goto(url)`
- Screenshot: `page.reload(wait_until="networkidle")` → `data = page.screenshot(full_page=False)` → `PIL.Image.open(io.BytesIO(data))`
- Thread safety: `_state_lock` protegge `_state`; `_page_lock` protegge l'intera sequenza `page.reload() + page.screenshot()`
- `_wait_for_server()`: poll `http://localhost:{port}/` ogni 0.5s con timeout 30s

**Criteri di accettazione:**
- `PlaywrightRenderer.screenshot()` restituisce un `PIL.Image` RGB di dimensioni `config.display.width × config.display.height`
- `get_state()` / `update_state()` sono thread-safe
- Su macOS senza `playwright_executable` usa il bundle Playwright senza errori

### 3.2 — Aggiornare `app/renderer/__init__.py`

```python
from app.renderer.playwright_renderer import PlaywrightRenderer

__all__ = ["PlaywrightRenderer"]
```

**Criteri di accettazione:** `from app.renderer import PlaywrightRenderer` funziona.

## Fase 4 — Refactor HdmiDisplay

**Goal:** `HdmiDisplay` usa Playwright non-headless (API Python) invece di subprocess Chromium.

*Dipende da: Fase 3.*

### 4.1 — Riscrivere `app/display/hdmi.py`

**Rimuovere:** import `subprocess`, `shutil`; metodi `_find_chromium()`, `_build_command()`; attributo `_proc`.

**Aggiungere:** import `from playwright.sync_api import sync_playwright`; attributi `_playwright`, `_browser`, `_page`.

**`start()` refactoring:**
```
HdmiDisplay.start()
  → thread daemon _run() che:
      → sync_playwright().start()
      → chromium.launch(headless=False, args=[...])
      → context.new_page().goto(url)
      → stop_event.wait()  # blocca il thread finché stop() non viene chiamato
```

**Nota threading:** `sync_playwright()` deve essere avviato e usato dallo stesso thread. `_run()` è il thread daemon dedicato che possiede il contesto Playwright.

**Criteri di accettazione:**
- `fullscreen: false` → finestra Chromium `width × height` su macOS
- `fullscreen: true` + `playwright_executable: /usr/bin/chromium-browser` → kiosk su RPi
- `HdmiDisplay.stop()` chiude la finestra senza errori

## Considerazioni

### Threading e Playwright sync API

Playwright `sync_playwright()` non è thread-safe. Due lock separati in `PlaywrightRenderer`:
- `_state_lock`: protegge la lettura/scrittura di `_state`
- `_page_lock`: protegge l'intera sequenza `page.reload() + page.screenshot()`

Se `update_state()` e `screenshot()` vengono chiamati concorrentemente (FastAPI POST /state + e-ink loop), i lock serializzano le operazioni. Overhead accettabile per intervalli ≥ 60s.

### HTMX e aggiornamento completo vs parziale

L'approccio scelto (POST /state restituisce l'intera nuova pagina, HTMX sostituisce `<body>`) è più semplice di partial updates e funziona correttamente per tutti i casi d'uso: HDMI (aggiornamento DOM via HTMX) ed e-ink (`page.reload()` sul prossimo ciclo di screenshot).

### HdmiDisplay e thread dedicato

`sync_playwright()` deve essere avviato e usato dallo stesso thread OS. `HdmiDisplay._run()` è il thread daemon dedicato che possiede il contesto Playwright; `start()` lancia il thread e ritorna immediatamente.
