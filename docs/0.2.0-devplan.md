# Development Plan — Family Planner v0.2.0

> Version: 0.2.0
> Date: May 23, 2026
> References: `docs/architecture.md`, `docs/design.md`, `docs/0.1.0-devplan.md`

---

## Version objective

v0.2.0 completes the migration to the new **Pillow + pygame** architecture (described in `AGENTS.md`), permanently abandoning the previous Chromium/Playwright-based approach. The architecture had already been implemented in code since v0.1.0; this version formalizes and extends it with three contributions:

1. **Updated `docs/architecture.md`** — the document still described the Chromium pipeline: it is rewritten to reflect the real codebase (Pillow + pygame + Waveshare).
2. **Navigation State API** — `GET /state` and `POST /state` to control navigation over HTTP from GPIO scripts, physical keyboard, or browser.
3. **Full web preview** — HTML templates for monthly, annual, daily, and detail views, upgrading the web server from partial preview (weekly only) to full preview of all five views.

---

## Invariant constraints (to be respected in every phase)

The v0.1.0 constraints remain unchanged:

- `ImageRenderer` (Pillow) is shared by both displays — no duplication of rendering logic
- Waveshare libraries are always imported dynamically, guarded by `display.type == "eink"`
- CalDAV credentials never appear in logs, API output, or error messages
- All file paths use `pathlib.Path`
- Standard logging (`logging`) — no diagnostic `print`
- Type hints are mandatory on all public functions
- No `box-shadow`, `border-radius`, `text-shadow` in HTML templates

## Phase 1 — Documentation alignment

**Goal:** `docs/architecture.md` describes the real architecture, no longer Chromium.

### 1.1 — Rewrite `docs/architecture.md`

Remove all references to Chromium, Playwright, kiosk mode, `inky` (Pimoroni). Replace them with the description of the actually implemented Pillow + pygame + Waveshare architecture. Update:

- **Technology stack**: Pillow for rendering, pygame for HDMI, Waveshare (dynamic import) for e-ink
- **Project structure**: add `renderer/` as the central layer (not post-processing), update `display/hdmi.py` and `display/eink.py`
- **Application flow**: `ImageRenderer.render()` → `HdmiDisplay` (pygame loop) / `EinkDisplay` (Waveshare push)
- **Display strategies**: no browser; `HdmiDisplay` reads directly from `ImageRenderer`
- **Navigation and state**: `NavigationState` (immutable dataclass) managed by `ImageRenderer` with threading lock, not by browser JS
- **Web routes**: add `GET /state` and `POST /state`; clarify that `GET /` is browser preview and configuration only
- **Dependencies**: remove `playwright`; confirm `pygame>=2.5`, `pillow`, optional Waveshare dependencies
- **Deploy scripts**: remove `playwright install` from `install.sh`
- **Component diagram**: update to reflect the real flow

**Acceptance criteria:** no occurrences of the words "Chromium", "Playwright", "kiosk", "inky", "Pimoroni" in the final document.

## Phase 2 — Navigation State API

**Goal:** navigation can be controlled over HTTP, enabling GPIO scripts and remote debugging.

### 2.1 — Add `get_state()` to `ImageRenderer`

**File:** `app/renderer/image_renderer.py`

Add a public method after `update_state()`:

```python
def get_state(self) -> NavigationState:
    """Thread-safe read of the current navigation state."""
    with self._lock:
        return self._state
```

This removes the need to access the private `_state` attribute from outside the renderer.

**Acceptance criteria:** `renderer.get_state()` returns a valid `NavigationState` without acquiring locks externally.

### 2.2 — Use `get_state()` in `HdmiDisplay`

**File:** `app/display/hdmi.py`

Replace direct access to `renderer._state` and `renderer._lock` (pattern `with self._renderer._lock: current_state = self._renderer._state`) with:

```python
current_state = self._renderer.get_state()
```

Occurrences are in `_handle_key()` and `_handle_click()`. Behavior remains identical — thread safety is guaranteed by the internal lock in `get_state()`.

**Acceptance criteria:** `hdmi.py` no longer accesses renderer private attributes (`_lock`, `_state`).

### 2.3 — Add `renderer` as a parameter to `create_app()`

**File:** `app/server/app.py`

Update the `create_app()` signature to accept an `ImageRenderer`:

```python
from app.renderer.image_renderer import ImageRenderer

def create_app(
    config: AppConfig,
    aggregator: CalendarAggregator,
    config_path: Path,
    renderer: ImageRenderer,
) -> FastAPI:
    ...
    app.state.renderer = renderer
```

Register the new `state_router`:

```python
from app.server.routes.state import router as state_router
...
app.include_router(state_router)
```

**Acceptance criteria:** `request.app.state.renderer` is available in all routes.

### 2.4 — Move renderer creation to `main.py`

**File:** `app/main.py`

The renderer was created inside each branch (`hdmi` / `eink`). Move it before the conditional block so it is always available:

```python
renderer = ImageRenderer(aggregator, config.display)

if config.display.type == "hdmi":
    display_obj = HdmiDisplay(config.display, renderer, aggregator)
elif config.display.type == "eink":
    ...

web_app = create_app(config, aggregator, config_path, renderer)
```

**Acceptance criteria:** `python app/main.py --config config/default.yaml` starts without errors.

### 2.5 — Create `app/server/routes/state.py`

New file with two routes:

**`GET /state`** — returns the current state as JSON:

```json
{
  "view": "weekly",
  "selected_date": "2026-05-23",
  "selected_event_uid": null,
  "detail_scroll_offset": 0,
  "night_mode": false
}
```

**`POST /state`** — accepts `{"action": "<value>"}` and returns the new state. Accepted values:

| `action` | `NavigationState` method |
|---|---|
| `"prev"` | `navigate_up(events)` |
| `"next"` | `navigate_down(events)` |
| `"in"` | `navigate_enter(events)` |
| `"out"` | `navigate_escape()` |
| `"night"` | `toggle_night_mode()` |

Actions `prev`, `next`, and `in` require the event list for contextual selection: the route fetches events for the current view range before invoking the method.

**Acceptance criteria:**

```bash
curl http://localhost:8080/state
# → {"view":"weekly", ...}

curl -X POST http://localhost:8080/state \
     -H "Content-Type: application/json" \
     -d '{"action":"next"}'
# → updated state
```

## Phase 3 — Full web preview

**Goal:** `GET /` supports all five views via the `?view=` parameter; each view has its own Jinja2 template.

### 3.1 — Update `app/server/routes/index.py`

Update the `GET /` route to accept the optional `?view=annual|monthly|weekly|daily|detail` parameter:

- If `view` is not specified: read the current view from `renderer.get_state().view`
- Dispatch to the appropriate view function
- The `?week=N` parameter remains for backward compatibility with the weekly view

Add helper functions:

| Function | Template | Key data |
|---|---|---|
| `_weekly_view(request, week)` | `calendar.html` | 7-day hourly event grid |
| `_monthly_view(request)` | `monthly.html` | 7×5/6 grid, events per day |
| `_annual_view(request)` | `annual.html` | 12 mini-calendars, presence indicators |
| `_daily_view(request)` | `daily.html` | 08–22 hourly grid for a single day |
| `_detail_view(request)` | `detail.html` | single event by UID |

Add data builders:

- `_build_month_grid(year, month, events, today)` → list of weeks (list of day dicts)
- `_build_annual_months(year, events, today)` → list of 12 months with mini-calendar data
- `_find_event_by_uid(aggregator, uid, around)` → `CalendarEvent | None`

**Acceptance criteria:**

```
GET /?view=monthly    → 200, monthly.html template
GET /?view=annual     → 200, annual.html template
GET /?view=daily      → 200, daily.html template
GET /?view=detail     → 200, detail.html template (or daily if no event is selected)
GET /                 → 200, current view from renderer state
```

### 3.2 — Template `app/server/templates/monthly.html`

Extends `base.html`. Layout:

- **Header**: month name + year, buttons ← (previous month) and → (next month)
- **Grid**: 7-column header (MON–SUN) + N rows (weeks covering the month)
- **Day cell**: day number + up to 3 event pills (colored dot + truncated title) + overflow `+N`
- **Today**: day number with `--color-accent` background
- **Days from other months**: number with `--color-ink-faint`

### 3.3 — Template `app/server/templates/annual.html`

Extends `base.html`. Layout:

- **Header**: year + buttons ← →
- **3×4 grid**: 12 monthly mini-calendars
- **Mini-calendar**: month header (in `--color-accent` for current month), weekday header (M T W T F S S at 8px), compact number grid
- **Event indicator**: 3×3px colored dot below the number, absent for the current day (which has `--color-accent` background)

### 3.4 — Template `app/server/templates/daily.html`

Extends `base.html`. Layout identical to the weekly grid but with a single column:

- **Header**: full date (e.g., "Wednesday, May 23, 2026"), "Today" badge if applicable, buttons ← →
- **All-day strip**: all-day events with colored dot, `all day` label if empty
- **08–22 grid**: same logic as `calendar.html` but for one day, full width

### 3.5 — Template `app/server/templates/detail.html`

Extends `base.html`. Layout:

- **Color strip**: 3px bar using the calendar color
- **Title**: Playfair Display, text-xl
- **Date/time meta row**: calendar icon + formatted datetime string
- **Calendar meta row**: clock icon + calendar name
- **Location meta row** (if present): pin icon + text
- **Recurring meta row** (if `event.recurrent`): loop icon + "Yes"
- **Description** (if present): pre-wrap text, top border, body font
- **Attendees** (if present): mono-font list, top border
- **Scroll**: `detail-body` is `overflow-y: auto` — only scrollable area in the UI
