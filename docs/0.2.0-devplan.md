# Piano di Sviluppo — Family Planner v0.2.0

> Versione: 0.2.0
> Data: 23 maggio 2026
> Riferimenti: `docs/architecture.md`, `docs/design.md`, `docs/0.1.0-devplan.md`

---

## Obiettivo della versione

v0.2.0 completa la migrazione verso la nuova architettura **Pillow + pygame** (descritta in `AGENTS.md`), abbandonando definitivamente l'approccio precedente basato su Chromium/Playwright. L'architettura era già implementata nel codice da v0.1.0; questa versione la formalizza e la estende con tre contributi:

1. **`docs/architecture.md` aggiornato** — il documento descriveva ancora la pipeline Chromium: viene riscritto per riflettere il codice reale (Pillow + pygame + Waveshare).
2. **Navigation State API** — `GET /state` e `POST /state` per controllare la navigazione via HTTP da script GPIO, tastiera fisica o browser.
3. **Anteprima web completa** — template HTML per le viste mensile, annuale, giornaliera e dettaglio, portando il server web da anteprima parziale (solo settimanale) ad anteprima completa di tutte e cinque le viste.

---

## Vincoli invarianti (da rispettare in ogni fase)

I vincoli di v0.1.0 rimangono invariati:

- `ImageRenderer` (Pillow) è condiviso da entrambi i display — nessuna duplicazione della logica di rendering
- Le librerie Waveshare sono sempre importate dinamicamente, protette da `display.type == "eink"`
- Le credenziali CalDAV non appaiono mai in log, output API o messaggi di errore
- Tutti i percorsi file usano `pathlib.Path`
- Logging standard (`logging`) — nessun `print` diagnostico
- Type hints obbligatori su tutte le funzioni pubbliche
- Nessun `box-shadow`, `border-radius`, `text-shadow` nei template HTML

## Fase 1 — Allineamento documentazione

**Goal:** `docs/architecture.md` descrive l'architettura reale, non più Chromium.

### 1.1 — Riscrivere `docs/architecture.md`

Rimuovere tutti i riferimenti a Chromium, Playwright, kiosk mode, `inky` (Pimoroni). Sostituire con la descrizione dell'architettura Pillow + pygame + Waveshare effettivamente implementata. Aggiornare:

- **Stack tecnologico**: Pillow per rendering, pygame per HDMI, Waveshare (import dinamico) per e-ink
- **Struttura del progetto**: aggiungere `renderer/` come layer centrale (non come post-processing), aggiornare `display/hdmi.py` e `display/eink.py`
- **Flusso applicativo**: `ImageRenderer.render()` → `HdmiDisplay` (pygame loop) / `EinkDisplay` (Waveshare push)
- **Strategie di display**: nessun browser; `HdmiDisplay` legge direttamente dall'`ImageRenderer`
- **Navigazione e stato**: `NavigationState` (dataclass immutabile) gestito dall'`ImageRenderer` con lock threading, non dal browser JS
- **Rotte web**: aggiungere `GET /state` e `POST /state`; precisare che `GET /` è solo anteprima browser e configurazione
- **Dipendenze**: rimuovere `playwright`; confermare `pygame>=2.5`, `pillow`, dipendenze Waveshare opzionali
- **Script di deploy**: rimuovere `playwright install` da `install.sh`
- **Diagramma componenti**: aggiornare per riflettere il flusso reale

**Criteri di accettazione:** nessuna occorrenza delle parole "Chromium", "Playwright", "kiosk", "inky", "Pimoroni" nel documento finale.

## Fase 2 — Navigation State API

**Goal:** la navigazione può essere controllata via HTTP, abilitando script GPIO e debug remoto.

### 2.1 — Aggiungere `get_state()` a `ImageRenderer`

**File:** `app/renderer/image_renderer.py`

Aggiungere metodo pubblico dopo `update_state()`:

```python
def get_state(self) -> NavigationState:
    """Thread-safe read of the current navigation state."""
    with self._lock:
        return self._state
```

Elimina la necessità di accedere all'attributo privato `_state` dall'esterno del renderer.

**Criteri di accettazione:** `renderer.get_state()` restituisce una `NavigationState` valida senza acquisire lock dall'esterno.

### 2.2 — Usare `get_state()` in `HdmiDisplay`

**File:** `app/display/hdmi.py`

Sostituire gli accessi diretti a `renderer._state` e `renderer._lock` (pattern `with self._renderer._lock: current_state = self._renderer._state`) con:

```python
current_state = self._renderer.get_state()
```

Le occorrenze si trovano in `_handle_key()` e `_handle_click()`. Il comportamento è identico — la thread-safety è garantita dal lock interno di `get_state()`.

**Criteri di accettazione:** `hdmi.py` non accede più ad attributi privati del renderer (`_lock`, `_state`).

### 2.3 — Aggiungere `renderer` come parametro di `create_app()`

**File:** `app/server/app.py`

Aggiornare la firma di `create_app()` per accettare un `ImageRenderer`:

```python
from app.renderer.image_renderer import ImageRenderer

def create_app(
    config: AppConfig,
    aggregator: CalendarAggregator,
    config_path: Path,
    renderer: ImageRenderer,
) -> FastAPI:
    ...
    app.state.renderer = renderer
```

Registrare il nuovo `state_router`:

```python
from app.server.routes.state import router as state_router
...
app.include_router(state_router)
```

**Criteri di accettazione:** `request.app.state.renderer` è disponibile in tutte le route.

### 2.4 — Spostare la creazione del renderer in `main.py`

**File:** `app/main.py`

Il renderer era creato all'interno di ciascun branch (`hdmi` / `eink`). Spostarlo prima del blocco condizionale in modo che sia sempre disponibile:

```python
renderer = ImageRenderer(aggregator, config.display)

if config.display.type == "hdmi":
    display_obj = HdmiDisplay(config.display, renderer, aggregator)
elif config.display.type == "eink":
    ...

web_app = create_app(config, aggregator, config_path, renderer)
```

**Criteri di accettazione:** `python app/main.py --config config/default.yaml` si avvia senza errori.

### 2.5 — Creare `app/server/routes/state.py`

Nuovo file con due route:

**`GET /state`** — restituisce lo stato corrente come JSON:

```json
{
  "view": "weekly",
  "selected_date": "2026-05-23",
  "selected_event_uid": null,
  "detail_scroll_offset": 0,
  "night_mode": false
}
```

**`POST /state`** — accetta `{"action": "<valore>"}` e restituisce il nuovo stato. Valori accettati:

| `action` | Metodo `NavigationState` |
|---|---|
| `"prev"` | `navigate_up(events)` |
| `"next"` | `navigate_down(events)` |
| `"in"` | `navigate_enter(events)` |
| `"out"` | `navigate_escape()` |
| `"night"` | `toggle_night_mode()` |

Le azioni `prev`, `next`, `in` richiedono la lista eventi per la selezione contestuale: il route fetcha gli eventi per il range della vista corrente prima di invocare il metodo.

**Criteri di accettazione:**

```bash
curl http://localhost:8080/state
# → {"view":"weekly", ...}

curl -X POST http://localhost:8080/state \
     -H "Content-Type: application/json" \
     -d '{"action":"next"}'
# → stato aggiornato
```

## Fase 3 — Anteprima web completa

**Goal:** `GET /` supporta tutte e cinque le viste via parametro `?view=`; ogni vista ha il proprio template Jinja2.

### 3.1 — Aggiornare `app/server/routes/index.py`

Aggiornare la route `GET /` per accettare il parametro opzionale `?view=annual|monthly|weekly|daily|detail`:

- Se `view` non è specificato: legge la vista corrente da `renderer.get_state().view`
- Dispatcha alla funzione di view appropriata
- Il parametro `?week=N` rimane per retrocompatibilità con la vista settimanale

Aggiungere le funzioni helper:

| Funzione | Template | Dati chiave |
|---|---|---|
| `_weekly_view(request, week)` | `calendar.html` | griglia eventi oraria 7 giorni |
| `_monthly_view(request)` | `monthly.html` | griglia 7×5/6, eventi per giorno |
| `_annual_view(request)` | `annual.html` | 12 mini-calendari, indicatori presenza |
| `_daily_view(request)` | `daily.html` | griglia oraria 08–22 giorno singolo |
| `_detail_view(request)` | `detail.html` | evento singolo per UID |

Aggiungere i builder di dati:

- `_build_month_grid(year, month, events, today)` → lista di settimane (lista di dict giorno)
- `_build_annual_months(year, events, today)` → lista di 12 mesi con dati per mini-calendario
- `_find_event_by_uid(aggregator, uid, around)` → `CalendarEvent | None`

**Criteri di accettazione:**

```
GET /?view=monthly    → 200, template monthly.html
GET /?view=annual     → 200, template annual.html
GET /?view=daily      → 200, template daily.html
GET /?view=detail     → 200, template detail.html (o daily se nessun evento selezionato)
GET /                 → 200, vista corrente dal renderer state
```

### 3.2 — Template `app/server/templates/monthly.html`

Estende `base.html`. Layout:

- **Header**: nome mese + anno, pulsanti ← (mese prec.) e → (mese succ.)
- **Griglia**: intestazione 7 colonne (LUN–DOM) + N righe (settimane che coprono il mese)
- **Cella giorno**: numero giorno + fino a 3 event pill (dot colorato + titolo troncato) + overflow `+N`
- **Oggi**: numero giorno con background `--color-accent`
- **Giorni altri mesi**: numero con `--color-ink-faint`

### 3.3 — Template `app/server/templates/annual.html`

Estende `base.html`. Layout:

- **Header**: anno + pulsanti ← →
- **Griglia 3×4**: 12 mini-calendari mensili
- **Mini-calendario**: intestazione mese (in `--color-accent` per mese corrente), intestazione giorni (L M M G V S D in 8px), griglia compatta di numeri
- **Indicatore eventi**: dot colorato 3×3px sotto il numero, assente per il giorno corrente (che ha sfondo `--color-accent`)

### 3.4 — Template `app/server/templates/daily.html`

Estende `base.html`. Layout identico alla griglia settimanale ma con una sola colonna:

- **Header**: data completa (es. "Mercoledì 23 Maggio 2026"), badge "Oggi" se è oggi, pulsanti ← →
- **Strip tutto il giorno**: eventi all-day con dot colorato, etichetta `tutto il giorno` se vuoto
- **Griglia 08–22**: stessa logica di `calendar.html` ma per un giorno solo, larghezza intera

### 3.5 — Template `app/server/templates/detail.html`

Estende `base.html`. Layout:

- **Strip colore**: barra 3px con il colore del calendario
- **Titolo**: Playfair Display, text-xl
- **Meta row data/ora**: icona calendario + stringa datetime formattata
- **Meta row calendario**: icona orologio + nome calendario
- **Meta row luogo** (se presente): icona pin + testo
- **Meta row ricorrente** (se `event.recurrent`): icona loop + "Sì"
- **Descrizione** (se presente): testo pre-wrap, bordo superiore, font body
- **Partecipanti** (se presenti): lista font-mono, bordo superiore
- **Scroll**: il `detail-body` è `overflow-y: auto` — unico caso di scroll nella UI
