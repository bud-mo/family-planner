> Version: 0.9.0
> Date: June 20, 2026
> References: `docs/architecture.md`, `docs/design.md`, `docs/artworks.md`, `docs/0.7.0-devplan.md`, `docs/0.8.0-devplan.md`

---

## Version Objective

v0.9.0 is a **physical-interaction feature** release. It adds an automatic
**slideshow** to artwork/pictures mode, toggled by a dedicated physical button:

- While **artwork mode is active** (either `source: endpoint` or `source: folder`),
  a single press of button **C** — or its rotation-equivalent when the panel is
  mounted upside-down — **toggles slideshow mode on/off**.
- When slideshow is **on**, the panel advances to the **next image at a regular
  interval** (next folder picture in `folder` mode; a fresh random painting in
  `endpoint` mode), exactly as a manual artwork-button press would, but on a timer.
- The interval is **configurable in minutes** (`artwork.slideshow_interval_minutes`),
  **default 30**, editable from the `/config` web UI.
- Slideshow auto-stops when artwork mode is left (planner button) or the device
  shuts down. Pressing C again while slideshow is on turns it off (the current
  image stays — e-ink is bistable).

This release does **not** change the rendering pipeline, the artwork fetch/folder
logic, the ARTIC integration, or the e-ink push mechanics. A slideshow "tick" is
literally the same `render_artwork() → process_photo() → display.push()` cycle the
artwork button already performs ([main.py:432-468](../app/main.py#L432)); the new
code is the **timer that drives it** and the **button that toggles it**.

**Release closure criterion:** on an Inky Impression, entering artwork mode and
pressing button C starts an interval rotation at the configured cadence; pressing
C again stops it; leaving artwork mode stops it; the interval is read from config
(default 30 min) and editable from `/config`; the new logic is covered by unit
tests with no real GPIO/network; the full suite is green.

## The central risk — button C and the BCM16 / SPI-CS1 question

This must be resolved **before** Phase 4, because it decides whether the headline
button works on standard panels.

**The conflict.** The four Inky Impression buttons map to BCM **A=5, B=6, C=16,
D=24**. On every model except the 13.3″, **BCM16 is also SPI CS1**, used by the
Inky driver. Historically this is why button C was described as "not acquired".

**The contradiction in the tree today.**

- `docs/AGENTS.md` and the **file-level docstring** of
  [app/display/buttons.py:5-10](../app/display/buttons.py#L5) still claim *"Only
  buttons A, B and D are requested … button C (BCM16) is not acquired"*.
- The **actual code** does the opposite: `_BUTTON_PINS_DEFAULT` includes `"C": 16`
  ([buttons.py:42](../app/display/buttons.py#L42)) and `_listen` requests **all
  four** lines in one block (`pins = tuple(self._button_pins.values())`,
  [buttons.py:165](../app/display/buttons.py#L165)).
- More tellingly, the **inverted-rotation mapping already uses C as the artwork
  button** (`_artwork_button = "C" if _inverted_rotation else "B"`,
  [main.py:660](../app/main.py#L660)). So a 180°/270° install **already depends on
  C=BCM16 firing**. If C were truly unacquirable, inverted-mode artwork would
  already be broken.

**Conclusion for the plan.** The docstring/AGENTS note is **stale**; the code's
intent is that all four lines are requested and C is usable. Wiring slideshow to C
is therefore *consistent with code that already ships*. **But** BCM16/SPI-CS1
behaviour can differ across RPi models, kernels, and device-tree overlays, so this
release must:

1. **Verify on real hardware** (Phase 4 acceptance) that, in **standard**
   orientation, button C produces a falling-edge event while the Inky SPI driver
   holds CS1 — i.e. `gpiod.request_lines({(5,6,16,24): …})` succeeds and C fires.
   On the **13.3″** model C is BCM25 (no conflict) and is the safe case.
2. **Fail safe if it cannot be acquired.** If, on a given board, requesting line 16
   alongside the others fails, the *current* code loses **all** buttons (one
   request block). Harden `_listen` to **fall back to requesting only the lines it
   can get** (drop C, keep A/B/D) and log which buttons are active, so a CS1
   conflict degrades slideshow only — never planner/artwork/shutdown. (See 1.2.)
3. **Document the real behaviour** and delete the stale "C not acquired" claims
   (Phase 6).

> Decision: **primary design = button C** (standard) / **B** (inverted), matching
> the existing 180° symmetry (A↔D, B↔C). A long-press / double-press of the
> artwork button was considered as a conflict-proof alternative but **rejected**:
> the user specified button C, the GPIO handler is a simple debounced falling-edge
> listener (no press-duration logic), and overloading the artwork button would
> remove its existing "advance to next image" manual press.

## Invariant Constraints

Constraints from previous versions remain valid. In particular for v0.9.0:

- **Slideshow is meaningful only inside artwork mode.** Toggling C while *not* in
  artwork mode is a **no-op** (logged at INFO). Leaving artwork mode (planner
  button) or shutdown **must** stop any running slideshow.
- **One image producer, one push path.** A slideshow tick reuses
  `PillowEinkRenderer.render_artwork()` + `EinkRenderer.process_photo()` +
  `InkyDisplay.push()` — it introduces **no** second rendering or push route.
- **Respect the panel push lock and settle race.** Every slideshow push goes
  through the same `display._push_lock` serialisation; consecutive panel refreshes
  must not violate the EL133UF1 settling window already handled for the planner
  return ([main.py:691-708](../app/main.py#L691)). The interval (≥1 min) is far
  larger than the settle window, so ticks never collide — but a tick that fires
  while a manual push is mid-flight must still serialise, not race.
- **Mode changes win over in-flight ticks.** If artwork mode is cleared (planner
  pressed) while a slideshow render/fetch is in progress, the push is **skipped**
  (same guard as `_perform_show_artwork._push`,
  [main.py:457-460](../app/main.py#L457)).
- **Interval is read live.** The slideshow controller reads
  `slideshow_interval_minutes` from current app state each cycle, so a SIGHUP
  config reload changes the cadence of the *next* interval without a restart.
- **CS1 conflict degrades slideshow only.** A board that cannot acquire BCM16 must
  still keep planner/artwork/shutdown working (Phase 1.2 fallback).
- **No config write / no SIGHUP from a button.** Toggling slideshow never rewrites
  the YAML; only the `/config` form save persists the interval (existing flow).
- **No e-ink panel ⇒ no slideshow.** In web-only mode (no panel) the controller is
  never started; the config field is still saved and shown.
- **Interval validation.** `slideshow_interval_minutes` is an `int ≥ 1`; invalid
  values are rejected by Pydantic at load and clamped in the UI.

## Phase 1 — Button-mapping helper + GPIO fallback

**Goal:** make the rotation→button mapping a **pure function** (today it is inline
in `main()` and untestable), extend it with the slideshow button, and make the
GPIO line request **degrade gracefully** if BCM16 cannot be acquired.

### 1.1 — Extract `resolve_button_roles`

The current inline block ([main.py:659-662](../app/main.py#L659)) computes three
roles from rotation. Replace it with a pure helper — put it next to the handler in
[app/display/buttons.py](../app/display/buttons.py) (or a small
`app/display/button_roles.py` if you prefer to keep `buttons.py` GPIO-only):

```python
def resolve_button_roles(rotation: int) -> dict[str, str]:
    """Map physical button labels (A/B/C/D) to roles for a given rotation.

    Standard (0°/90°):   A=planner  B=artwork  C=slideshow  D=shutdown
    Inverted (180°/270°): A=shutdown C=artwork  B=slideshow  D=planner

    The 180° flip swaps A↔D and B↔C, so every role keeps the same *physical*
    button position regardless of mounting orientation.
    """
    inverted = rotation in (180, 270)
    return {
        "planner":   "D" if inverted else "A",
        "artwork":   "C" if inverted else "B",
        "slideshow": "B" if inverted else "C",
        "shutdown":  "A" if inverted else "D",
    }
```

> This makes the **four-way** mapping explicit and is unit-testable
> (`tests/test_button_roles.py`). `main()` consumes the dict instead of three
> ad-hoc locals.

### 1.2 — Resilient line request (CS1 fallback)

In [buttons.py `_listen`](../app/display/buttons.py#L155), today a single
`request_lines({pins: settings})` either gets **all four** lines or, on failure,
logs and returns — losing every button. Change it to try the full set first and,
on failure, **retry without C** so a BCM16/CS1 conflict disables only slideshow:

```python
pins_all = tuple(self._button_pins.values())          # A,B,C,D
c_pin = self._button_pins["C"]
pins_no_c = tuple(p for p in pins_all if p != c_pin)

for pins in (pins_all, pins_no_c):
    try:
        request = gpiod.request_lines(chip_path, consumer="family-planner-buttons",
                                      config={pins: settings})
        break
    except Exception:
        logger.warning("InkyButtonHandler: richiesta linee %s fallita%s.",
                       pins, " — riprovo senza C (BCM%d)" % c_pin if pins is pins_all else "")
else:
    logger.exception("InkyButtonHandler: impossibile aprire le linee GPIO su %s.", chip_path)
    return

active = {lbl: pin for lbl, pin in self._button_pins.items()
          if pin in set(self._pin_to_label) and pin in <requested set>}
logger.info("InkyButtonHandler: pulsanti attivi: %s", ", ".join(active))
```

> Keep it minimal — the goal is only that *losing C never loses A/B/D*. Log the
> active set so a field diagnosis is one line in the journal. On the 13.3″ model
> C is BCM25 and the first attempt always succeeds.

**Acceptance — Phase 1:**

```bash
python -c "from app.display.buttons import resolve_button_roles as r; \
print(r(0)); print(r(180))"
# {'planner':'A','artwork':'B','slideshow':'C','shutdown':'D'}
# {'planner':'D','artwork':'C','slideshow':'B','shutdown':'A'}
```

## Phase 3 — Slideshow controller (testable)

**Goal:** the timer that drives auto-advance, isolated from GPIO and from `main()`
so it can be unit-tested with a fake clock and a stub push.

Create [app/display/slideshow.py](../app/display/slideshow.py) with a small
controller built on two `threading.Event`s already used elsewhere in the app
(`artwork_mode`) plus its own state:

```python
class SlideshowController:
    """Drives automatic artwork advancement on a configurable interval.

    A single worker thread sleeps `interval_minutes()` (read live each cycle),
    then performs one artwork advance+push, repeating until the slideshow is
    stopped, artwork mode is left, or the app stops. Toggling is idempotent and
    a no-op outside artwork mode.
    """

    def __init__(self, *, advance: Callable[[], None],
                 artwork_mode: threading.Event,
                 stop_event: threading.Event,
                 interval_minutes: Callable[[], int]) -> None:
        ...

    def toggle(self) -> None:
        """Start the slideshow if stopped, stop it if running. No-op if artwork
        mode is not active. Safe to call from the GPIO callback thread."""

    def stop(self) -> None:
        """Stop the slideshow if running (called when leaving artwork mode /
        shutting down). Idempotent."""

    @property
    def active(self) -> bool: ...
```

Internals:

- A `_active` flag + a `_cancel = threading.Event()`. `toggle()` while inactive and
  in artwork mode → set `_active`, clear `_cancel`, start `_run` thread; while
  active → clear `_active`, set `_cancel` (wakes the sleep so the thread exits).
- `_run`:

  ```python
  def _run(self):
      while self._active and self._artwork_mode.is_set() and not self._stop.is_set():
          # interruptible sleep: wake immediately on cancel/stop
          if self._cancel.wait(timeout=max(1, self._interval_minutes()) * 60):
              break                      # toggled off / stopped
          if not (self._artwork_mode.is_set() and self._active):
              break                      # mode changed during the wait
          try:
              self._advance()            # render_artwork → process_photo → push
          except Exception:
              logger.exception("slideshow: errore durante l'avanzamento.")
      self._active = False
      logger.info("Slideshow fermato.")
  ```

- The injected `advance` callable is supplied by `main()` (Phase 4) and is the
  *only* place that touches the renderer/display — keeping this module free of
  rendering and GPIO imports, hence trivially testable.

> Why a dedicated thread and not the existing `_eink_loop`? The e-ink loop ticks on
> **quarter-hour clock boundaries** and *suppresses* pushes during artwork mode by
> design ([main.py:330](../app/main.py#L330)). The slideshow interval is arbitrary
> (default 30 min, configurable to any ≥1) and must push *while* artwork mode is
> set — the opposite of the loop's contract. A separate, short-lived controller is
> cleaner than special-casing the loop.

**Acceptance — Phase 3:** see Phase 6.1 (fake-clock unit test).

## Phase 4 — Wire into `main()` + hardware verification

**Goal:** connect the button, the controller, and the existing artwork push;
verify on the device.

### 4.1 — Construct the controller and the advance callable

In [main.py](../app/main.py#L623), alongside `_artwork_mode` / `_wake_event`, after
the renderer/display are built:

```python
from app.display.slideshow import SlideshowController

def _advance_slideshow() -> None:
    # Reuse the artwork push WITHOUT resetting the folder cursor, so the
    # slideshow moves forward; mode-change guard mirrors _perform_show_artwork.
    img = _renderer_ref[0].render_artwork()
    if not _artwork_mode.is_set():
        logger.info("slideshow: avanzamento annullato (uscita da artwork).")
        return
    processed = _eink_renderer_ref[0].process_photo(img)
    display_obj.push(processed)
    logger.info("Slideshow: immagine successiva inviata al pannello.")

_slideshow = SlideshowController(
    advance=_advance_slideshow,
    artwork_mode=_artwork_mode,
    stop_event=eink_stop_event,
    interval_minutes=lambda: web_app.state.config.artwork.slideshow_interval_minutes,
)
```

> `render_artwork()` advances the folder cursor itself
> ([pillow_eink_renderer.py:224-229](../app/renderer/pillow_eink_renderer.py#L224))
> and fetches a fresh random work in endpoint mode, so the callable needs no extra
> cursor handling. Reading `interval_minutes` from `web_app.state.config` (not the
> captured `config`) makes SIGHUP changes take effect live.

### 4.2 — Replace the inline mapping and route the new button

Swap the three ad-hoc role locals for `resolve_button_roles(config.display.rotation)`
([main.py:659-662](../app/main.py#L659)), then in `_on_button`:

```python
roles = resolve_button_roles(config.display.rotation)

def _on_button(button: str) -> None:
    if _shutdown_triggered.is_set():
        return
    if button == roles["artwork"]:
        _perform_show_artwork(...)                 # unchanged
    elif button == roles["slideshow"]:
        _slideshow.toggle()                        # NEW — no-op outside artwork mode
    elif button == roles["planner"]:
        if _artwork_mode.is_set():
            _artwork_mode.clear()
            _slideshow.stop()                      # NEW — leaving artwork stops slideshow
        ...                                         # existing return-to-planner logic
    elif button == roles["shutdown"]:
        _slideshow.stop()                          # NEW — defensive
        _shutdown_triggered.set()
        ...                                         # existing shutdown logic
```

Update the startup log line to include the slideshow button
([main.py:726-732](../app/main.py#L726)).

> Note: when the user presses the **artwork** button again while slideshow is
> running, the existing `_perform_show_artwork` manually advances one image. That
> is harmless and intuitive (manual nudge) and does **not** stop the slideshow.
> Decide explicitly and document: manual advance ≠ slideshow toggle.

### 4.3 — Hardware verification (the gating step)

On the actual Inky Impression (both a standard model **and**, if available, the

## Phase 6 — Tests, documentation & closure

### 6.1 — `tests/test_slideshow.py`

Drive `SlideshowController` with **no real time and no GPIO**:

- inject `interval_minutes=lambda: ...` returning a tiny value and stub the
  `_cancel.wait` (or monkeypatch the sleep) so a "tick" is instantaneous; assert
  `advance` is called repeatedly while `artwork_mode`/`active` hold;
- `toggle()` outside artwork mode → `active is False`, `advance` never called;
- `toggle()` on then off → thread exits promptly, `advance` stops being called;
- clearing `artwork_mode` mid-run → loop exits, no further `advance`;
- `stop()` is idempotent and safe when already stopped;
- an exception thrown by `advance` is swallowed and the loop keeps/stops per state
  (never crashes the thread).

Use a `threading.Event` + a short join with timeout to assert termination; keep the
test deterministic (no `sleep`-based races — gate on a `Condition`/counter).

- `resolve_button_roles(0)` and `(90)` → standard map (slideshow=C);

## Out of Scope

- A per-image or per-source independent interval; a single global interval only.
- Slideshow transitions/animations — e-ink refreshes are full-panel; a tick is one
  push.
- Persisting "slideshow was on" across reboots — it always starts off; the bistable
  panel keeps the last image after shutdown.
- Random vs sequential ordering controls — folder stays alphabetical, endpoint stays
  random (unchanged from artwork mode).
- A web-UI start/stop button or live status for slideshow — it is a physical-button
  feature; the UI only sets the interval.
- Press-duration logic (long/double press) in the GPIO handler — the handler stays a
  debounced single-edge listener.
- Any change to the renderer, ARTIC fetch, folder management (v0.8.0), or e-ink push
  mechanics.
